# Superoptimizer task - the INDUCE law: how the system grows new knowledge

**Not authored here.** The defect, the measurement, the bits and the principles - no formula, no table. Your engine
authors the expression; `judge_induce.py` judges it by enumeration.

---

## What exists - the loop learns, laws end to end

| law | decides | judged | live on click |
|---|---|---|---|
| `pick` | which mutation to try next | 0 violations, unique | 5 trials chosen, 5 taken |
| `harvest` | keep / skip / recheck / stop a trial | 0 violations, unique | 5 examples in 20 suite runs |
| `route4d5` | the whole kind -> act relabelling from 5 examples | 0 violations; 50,000/50,000 harvest-shaped answered | **60/60 real decisions, 0 wrong**, two secret renumberings |

## The defect

That loop learns the **mapping** for classes it already has. It never learns a **new class**. Every class in its
vocabulary was written by a person - fluidfix's nine shipped, fluidnet's taught ones - or, in fluidnet, handed in
by an AI body. A system that is meant to grow its knowledge from whatever it is pointed at needs the missing step:
**turn a change it keeps seeing into a class it knows** - and never admit one that would ship a wrong fix.

## What a candidate class is

A recurring change mined from what the system is pointed at - a repository's history, a stream of fixes: the same
one-token change, `old -> new`, in different places. As a class it is complete and mechanical:

- **signal:** the lines where `old` occurs
- **rewrite:** `old -> new` at that token
- **property:** exactly one token changes, and it changes from `old` to `new` - checkable on every candidate,
  the way fluidnet's taught `rename` classes are guarded

Once admitted, HARVEST and PICK learn its act code from the target's own tests, and the 4D router generalises it.

## The measurement - why induction must be strict (`results/induce_motivation.json`)

Every one-line fix in BugsInPy, Defects4J and Defects4C - 1,729 real bugs, across projects:

| | |
|---|---|
| fixes that change exactly one token | 334 |
| distinct `old -> new` patterns among them | 188 |
| patterns seen in **two or more different bugs** | **15** - covering 41 of the 334 fixes (12%) |
| patterns seen in five or more | 0 |
| held out, generated by a pattern induced from the other bugs | 41 of 334 (12%) |
| `<` -> `<=`: real fixes vs the changed lines its signal fires on | **4 vs 191** |

Most changes happen once; a pattern that recurs fires far more often than it is right. Within ONE project's history
recurrence is higher - fluidnet's own replay of 565 real maintainer fixes in commit order measured 16% exact
repeats and 38% at the level of pattern families, **rising 31% -> 40% -> 43%** from early to late history. Growth is
real, and slow, and the noise is large: so a class is admitted only when the future confirms it, a property guards
it, and the suite stays the only acceptor.

## The decision

For ONE candidate class - a mined pattern, or a class already in the vocabulary under review - what to do with it,
decided from eight measured bits and nothing else.

## The measurement the body will supply

| bit | name | set when |
|---|---|---|
| 0 | `SEEN2` | the pattern occurred in at least two independent fixes (different bugs, different commits) |
| 1 | `SEEN5` | in at least five |
| 2 | `CONFIRMED` | induced from fixes before time t, it generated a LATER held-out fix exactly - prospective, never fitted after the fact |
| 3 | `REFUTED` | on a held-out fix it produced a candidate the suite accepted that was not the real fix (a confident wrong fix it would have shipped), or a real fix of its shape broke its property |
| 4 | `PROVABLE` | the class carries a mechanical property every rewrite is checked against |
| 5 | `CONFLICT` | an admitted class has the same signal with a different rewrite - the two would compete on the same lines |
| 6 | `NOISY` | its signal fires on more than 5% of the target's source lines |
| 7 | `ADMITTED` | the class is already in the vocabulary - this decision is a review |

**Situation word:** `x = SEEN2 | SEEN5 << 1 | CONFIRMED << 2 | REFUTED << 3 | PROVABLE << 4 | CONFLICT << 5 |
NOISY << 6 | ADMITTED << 7`

**Unreachable** (the law may return anything there, but must land in 0..3):
- `SEEN5` without `SEEN2`.
- `CONFIRMED` without `SEEN2` - a confirmation is itself a second occurrence.

That leaves **160 reachable values of 256.**

## The law to find

```
induce(x) -> 0..3
   0  REJECT   forget the candidate
   1  KEEP     no change - a candidate keeps being watched, an admitted class stays
   2  ADMIT    add it to the vocabulary; HARVEST and PICK learn its act, the router generalises it
   3  RETIRE   remove an admitted class
```

## The principles - stated as "exactly when", so they force every cell

- **I0 A refuted class never stays.** `REFUTED`: RETIRE if `ADMITTED`, REJECT if not. One confident wrong fix is
  disqualifying - fluidnet's founding lesson, a rewrite a weak suite accepted.
- **I1 ADMIT exactly when proven prospectively, guarded and uncontested.** Not `ADMITTED`, not `REFUTED`, and
  `CONFIRMED`, `PROVABLE`, `SEEN2`, not `CONFLICT`, and (not `NOISY` or `SEEN5`): ADMIT - and ADMIT in no other
  case. Strong support may outweigh a noisy signal; nothing outweighs a missing confirmation or a missing property.
- **I2 An admitted, unrefuted class stays.** `ADMITTED` and not `REFUTED`: KEEP - a newcomer's conflict does not
  evict an incumbent; it blocks the newcomer (I1).
- **I3 Otherwise keep watching.** Not `ADMITTED`, not `REFUTED`, not admissible: KEEP. A pattern seen once is the
  common case, not a reason to forget it.
- **I4 RETIRE only an admitted, refuted class.**
- **I5 REJECT only a refuted candidate.**

**Checked before asking: the principles fix every cell.** `judge_induce.py --selfcheck` shows exactly one table
satisfies I0-I5 on the 160 reachable words (built only to be perturbed - not handed over); every single-cell change
to it breaks at least one principle. On reachable words that table ADMITs in 3 situations of 160 - induction is
meant to be rare.

## Constraints

- **Branchless integer arithmetic over `x`**; shifts, masks, adds, subtracts, popcount and `ntzb` if your engine has
  them, defined in the file itself. Fewer operations is better.
- **Total** on 0..255, landing in 0..3; **exact** on every reachable word.
- Signature: `int32_t induce(int32_t x)`.

## How it will be judged

```bash
.venv/bin/python judge_induce.py laws/induce.c
```

I0-I5 by enumeration on every reachable word, the range on all 256, and every single-cell change to the kernel's
own table must break a principle. Then live - **the learning curve**: replay a real project's history in commit
order (click's full git history is on disk), mine `old -> new` patterns as fixes arrive, let INDUCE admit, keep
and retire, let HARVEST and PICK learn each admitted class's act from the project's own tests, and route with
`route4d5`. Measured over time: the share of each *future* fix the system's knowledge generates - if it rises,
the system is learning - and the number of wrong fixes it would have shipped, which must stay 0.

**What the superoptimizer does not decide:** the thresholds behind the bits (two and five occurrences, 5% of lines),
how patterns are mined (one token today; AST-level shapes next), and when the vocabulary outgrows the 8-cell's 16
kinds and moves to the 600-cell's 120. Those are the body's; if the learning curve says they are wrong, the
measurement changes, never the table.
